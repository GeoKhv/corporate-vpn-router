# Сертификаты и разрешения Check Point

В публичный пакет не включены корпоративные сертификаты. Для каждого компьютера мастер проверяет фактические цепочки. Наличие CA в Keychain и успешный TLS означают доверие данного компьютера; они не доказывают, что сертификат выпущен вашей организацией законно. Подлинность подтверждает ИТ-служба по независимому каналу.

## Что может потребоваться

| Компонент | Когда нужен | Действие |
|---|---|---|
| Корневой CA корпоративного HTTPS | Если рабочие серверы используют частную PKI, которой система ещё не доверяет | Получить у ИТ-службы файл, SHA-256 и разрешение; подтвердить импорт |
| Промежуточный CA | Если сервер не отдаёт полную цепочку или локальная система её не строит | Сначала исправить серверную цепочку с ИТ-службой; при согласованной установке импортировать без Always Trust |
| CA HTTPS-инспекции | Только если инспекция действительно применяется и подтверждена организацией | Проверять отдельно; не объявлять любой неизвестный issuer инспекцией |
| Сертификат сервера HTTPS | Предъявляется сервером; не устанавливается как доверенный корень | Проверяется имя, цепочка и срок; исправляется на стороне сервера |
| Сертификат VPN/IKE-шлюза и pin сайта | Зависит от Check Point и его политики | Подтверждение в штатном Check Point/ИТ-службе; HTTPS входной страницы не доказывает IKE-цепочку |
| Пользовательский/машинный сертификат с приватным ключом | Только при соответствующем способе авторизации | Индивидуальная выдача/MDM/smart card по процедуре организации; мастер не импортирует PFX и ключи |
| Дополнительные CA из старых инструкций | Не обязательно | Не устанавливать, пока не установлена необходимость и подлинность |

## Мастер macOS

Откройте **Certificates & Permissions…** в установленном приложении. Сначала задайте корпоративные DNS и домены в главном окне и сохраните конфигурацию. В мастере перечислите точные HTTPS-хосты (например, почта, Jira, Confluence) и нажмите **Check HTTPS & permissions**.

Для каждого хоста проверяются корпоративный путь, DNS, TLS с именем сервера, системное доверие цепочке, сроки, SHA-256, наличие публичных сертификатов в login/System/System Roots и ответ HTTPS HEAD. Пароли, cookies и приватные ключи не читаются. При запросе клиентского сертификата мастер останавливается и направляет к индивидуальному корпоративному enrollment.

TLS-проверка не загружает AIA/OCSP/CRL через обычный маршрут. Поэтому она не является полной онлайн-проверкой отзыва; недостающая цепочка может потребовать исправления сервером или согласованного импорта промежуточного CA. Ошибка доверия никогда не превращается в разрешение продолжить HTTPS.

Кнопка **Site HTTPS** отдельно проверяет только настроенную в Check Point HTTPS-точку входа по обычному системному маршруту, после отдельного подтверждения. Эта точка должна быть доступна до туннеля. Это не запрос рабочего сервиса и не обследование IKE-сертификата VPN.

## Безопасный импорт

1. Получите один публичный `.cer`/`.crt`/`.pem`/`.der` из авторизованного корпоративного источника. Отдельным доверенным каналом сверьте SHA-256, назначение CA и разрешение на его установку. Сам файл, серверная цепочка и установленный Keychain не являются независимым каналом.
2. Нажмите **Review CA file…**. Сверьте Subject, Issuer, сроки и SHA-256. Мастер отвергает ключи, PFX/P12 и PEM-пакеты из нескольких сертификатов.
3. Укажите HTTPS-ссылку на источник без паролей и query-токенов. Вставьте независимо подтверждённый отпечаток и отметьте подтверждение ИТ-канала.
4. Нажмите **Review & Import…** и подтвердите конкретный сертификат в отдельном диалоге. Затем macOS может запросить собственную авторизацию.
5. Корень получает доверие только в пользовательском домене для SSL. Это доверие действует шире Router, что явно указано в диалоге. Промежуточный CA импортируется без изменения доверия. Системное/административное хранилище не меняется.
6. Повторите **Check HTTPS & permissions**. Успешный импорт сам по себе не доказывает успешный HTTPS или подлинность источника.

Уже имеющиеся сертификаты мастер не заменяет и их trust settings не меняет. Если имеющийся CA не доверен, требуется ручная проверка с ИТ-службой. Для отмены только новых импортов предусмотрен **Undo an import…**, точное сравнение отпечатка и отдельное согласие. Квитанции хранятся локально с правами пользователя. Нельзя распространять сертификаты организации без разрешения.

## Разрешения Check Point

Автоматически проверяются наличие CLI, валидность подписи установленного приложения, ответ vendor-сервиса, состояние подключения, доступные признаки Network Extension, тип авторизации и число валидных TLS-клиентских идентичностей в пользовательском поиске. Никакие ключи не экспортируются.

Отсутствие записи Check Point в `systemextensionsctl` само по себе не доказывает ошибку: версии клиента используют разные механизмы. Подпись, живой сервис и туннель проверяются отдельно. Перечень approvals берётся из официальной инструкции именно к выданной вашей организацией версии. Мастер не запрашивает Full Disk Access, Accessibility или Screen Recording для Router и не меняет разрешения Check Point.

Пользователь/ИТ-служба подтверждает разрешение VPN-конфигурации, требуемого сетевого/системного расширения и фонового компонента в System Settings, если этого требует конкретный клиент. MDM-запрет нельзя обходить. Рабочий туннель подтверждает текущий обмен, но не сертифицирует все разрешения после следующего обновления/перезагрузки.

## Windows

Mac-мастер не является Windows-реализацией. Контракт отдельного адаптера описан в [плане Windows](../Platforms/Windows/README.md). До проверки на реальном Windows не распространяется ни установщик, ни утверждение о поддержке Windows.
