# Chrome без конфигурационного профиля macOS: исследование issue #1

Дата: 10 ноября 2026. База: `v0.2.0-beta.6`, commit `0fe83ba`.
[Задача #1](https://github.com/GeoKhv/corporate-vpn-router/issues/1).

**Результат: лабораторный прототип работает.** Перспективный вариант — один раз, при полностью закрытом браузере, записать пользовательскую настройку `proxy` в Chrome Preferences. После этого браузер запускается обычным способом, без расширения и параметров proxy. Но это внутренний формат Chrome, а не поддерживаемый API управления. На основном пользовательском профиле этот режим пока не принят. Установленная beta.6 остаётся основным режимом.

**Запуск только с `--proxy-server` уступает этому варианту:** холодный запуск работает, обычный следующий запуск теряет настройку. Добавление параметра уже работающему браузеру его сетевой контекст не перенастраивает.

## Сохранённая база и границы эксперимента

Установленную beta.6, конфигурационные профили macOS, рабочий список, LaunchAgents, основной Chrome и Sota не изменяли. Системные прокси Wi-Fi/Ethernet повторно не испытывали. Никакого нового релиза, обновления установленного приложения или изменений TLS/MFA нет.

Приватный каталог `.private/profile-free/` содержит точную копию установленного bundle, копии конфигурации, SHA-256 всех 572 файлов bundle и снимки состояния до/после. Совпали bundle, 13 файлов настроек, LaunchAgents, системный proxy и семантическое содержимое установленных конфигурационных профилей. Порядок payload в выводе `profiles show` меняется, поэтому сравнивается разобранный plist с нормализацией порядка словарей в массивах. Основной каталог Chrome сохранил inode; PID его процесса остался тем же. Снимок `scutil --nwi` совпал, Sota и исходный корпоративный SSL-сеанс остались активны. Проверена действующая forced-настройка Chrome на 1091 и SHA-256 архивов beta.6. Полный профиль Chrome с cookies/ключами не копировали.

На машине: macOS 27.0.1 arm64, обычный Chrome 157.0.8103.39. Для режима без политики использован официальный **Chrome for Testing 157.0.8103.38** с отдельным каталогом данных. У него отдельный policy domain `com.google.ChromeForTesting`; действующая политика `com.google.Chrome` его не контролирует. Это близкий контрольный браузер той же ветки, **не доказательство работы в основном профиле обычного Chrome**. Скачанный CfT имеет ad hoc подпись; его не выдавали за подписанный основной Chrome и не добавляли в доверенные MFA peers.

Work проверялся через уже аутентифицированный SOCKS beta.6 с неизменной проверкой владельца worker. Новый SSL-сеанс и новая Passkey/OTP-аутентификация в эксперименте не выполнялись. Отказ Work вводился только на границе отдельного тестового HTTP-router до обращения к SOCKS; живой SSL-worker не останавливали. Это проверка поведения браузера и разделения маршрутов при отказе, а не новый тест физического обрыва SSL.

## Варианты управления из приложения

### 1. Управляемый запуск существующего Chrome

Приложение может вызвать `NSWorkspace.openApplication` с `--proxy-server=http://127.0.0.1:1091`, сохранив стандартный каталог Chrome. Не нужны root, Accessibility, Automation или расширение. Адрес локального MFA callback продолжит пользоваться неявным обходом loopback; исключения и проверку подписанного Chrome менять не требуется.

Уже открытый Chrome необходимо сначала штатно завершить. Нельзя считать успех `open` доказательством настройки proxy: нужен случайный одноразовый HTTP witness на router. При запуске из Dock, Spotlight, ссылки, login restoration или после полного Quit параметры могут отсутствовать. Наблюдатель запуска обнаружит это уже после создания процесса и возможных сетевых запросов. Даже обычный успешный `open` не гарантирует, что новые параметры применились к старому процессу.

Такой режим подходит как явная команда «Открыть Chrome через Router», если пользователь принимает запуск через приложение. Он не обеспечивает устойчивый обычный запуск браузера. Переподписывание Chrome, изменение его Info.plist/исполняемого файла и подмена приложения не используются: это ломает поддержку обновлений и может затронуть доверие MFA/Keychain.

### 2. Пользовательский proxy в Preferences — работающий лабораторный кандидат

В `Default/Preferences` тестового профиля сохраняется:

```json
{"proxy":{"mode":"fixed_servers","server":"http://127.0.0.1:1091","bypass_list":""}}
```

Это выбирает тот же HTTP/CONNECT-router beta.6. Work/Life и изменения доменов остаются в приложении; каждый edit не требует новой записи в Chrome. Данные браузера не пересоздаются. Из архитектуры следует совместимость с существующими cookies и Passkey, однако реальная Passkey после такой миграции ещё не проверена.

Настройка относится к конкретному браузерному профилю, например Default или Profile 1. Другие и новые профили автоматически не покрываются. Пишущий приложение должно убедиться, что **весь Chrome закрыт**, сохранить прежнее значение, выполнить атомарную замену и проверить маршрут после запуска. Чтение/запись чужих данных приложения может вызвать отдельное разрешение macOS; на основном Chrome это не испытывалось. Admin, Network Extension и Accessibility для самого механизма не требуются.

Риски: внешний edit Preferences не является публичным API; работающий Chrome может перезаписать файл, а старт между проверкой процесса и записью создаёт гонку. Формат/защита предпочтения могут измениться при обновлении. Политика и управляющее расширение имеют приоритет. Прошедший тест близкого CfT не сертифицирует основной Chrome с его набором профилей, расширений и защитой настроек.

Прототип `Research/ChromeWithoutProfile/user_proxy.py` намеренно принимает **только отмеченные одноразовые каталоги**, отказывает при SingletonLock и конфликте proxy. Он умеет точный откат исходных байтов, если файл не менялся, и откат только собственного поля proxy после обычных изменений браузера. При конфликте чужая настройка не затирается. Это лабораторная защита, не законченный production installer и не полная защита от гонок с запуском Chrome.

### 3. `defaults write` и рекомендуемая политика

Это не найденный поддерживаемый способ обойти установку managed profile. Chromium классифицирует unforced CFPreferences как Recommended. У схемы `ProxySettings` нет разрешения `can_be_recommended`. Не следует путать запись обычного plist с установкой обязательной политики. В этом исследовании на production domain `com.google.Chrome` ничего не записывалось.

### 4. Network Extension

`NETransparentProxyProvider` — отдельная реалистичная архитектура для перехвата потоков независимо от способа запуска Chrome. Однако она требует Network Extension entitlements, подходящего подписания/provisioning и системного разрешения на расширение/сетевую конфигурацию. На этом Mac `security find-identity -v -p codesigning` сообщает **0 valid identities**. Текущая ad hoc beta.6 не даёт готовой возможности включить такой provider.

Нужно отдельно реализовать отбор Chrome-процессов, исключение собственных upstream-потоков, обработку TCP/UDP, DNS и проверку порядка взаимодействия с Sota. Это может сосуществовать с VPN в определённых конфигурациях, но на данном Mac совместимость не проверена и обещать её нельзя. Обычный `NEAppProxyProvider`/per-app VPN не является эквивалентом свободно устанавливаемого desktop HTTP proxy: у него другие требования к конфигурации. Network Extension сейчас дороже и требует больше разрешений, чем текущий профиль macOS; рабочим прототипом её не считаем.

## DNS и прямые соединения

Здесь DIRECT означает **вне корпоративного SSL-туннеля**, по текущему системному маршруту. При активной Sota это может быть маршрут Sota, а не физический выход провайдера. При отказе самой Sota выбор физического выхода определяется её настройками; Router не управляет её kill switch.

| Состояние | HTTP(S) Work | DNS и прочий трафик |
| --- | --- | --- |
| Fixed proxy применён, router и Work исправны | CONNECT по имени → restricted SOCKS → SSL | Рабочее разрешение адреса выполняет корпоративный packet tunnel. Life и точные beforeLogin-исключения используют системный resolver/маршрут |
| Корпоративный SOCKS/SSL недоступен | Router выдаёт ошибку, DIRECT-альтернативы для Work нет | Код router не вызывает direct resolver для Work. Независимые браузерные DNS/UDP-каналы этим утверждением не покрываются |
| HTTP-router недоступен, fixed proxy сохранён | Ошибка proxy у Work и Life | В проверенных запросах прямой HTTP(S) fallback не наблюдался. Это не гарантия отсутствия любого сетевого трафика Chrome |
| Chrome запущен без параметра, сохранённого pref и managed policy | Может попытаться соединиться с Work напрямую | A/AAAA/HTTPS DNS или DoH и прямой TCP/QUIC могут уйти по системной сети/Sota; внутреннее имя может раскрыться внешнему resolver даже при неуспешном соединении |
| User pref удалён/заменён; другой/новый профиль; конкурирующий контроллер | Зависит от фактически выбранной настройки | То же потенциальное раскрытие DNS и прямые попытки; приложение обнаружит смену только проверкой |
| Домен не попал в Work или намеренно исключён beforeLogin | Прямой системный путь по дизайну | Имя разрешается вне корпоративного туннеля. Ошибка списка опасна при обоих способах установки Chrome proxy |
| WebRTC, UDP, прямые IP, DNS prefetch/другие фоновые функции | За пределами доказанной HTTP(S) маршрутизации | Возможны STUN/TURN, mDNS/LAN и иные прямые потоки. Не утверждаем их полного отсутствия ни у прототипа, ни у beta.6 profile |
| Вариант с `--proxy-pac-url` | При сбое PAC возможен DIRECT | Командная настройка PAC создаётся с mandatory=false; fetch/cache PAC и сбой сервиса добавляют риск. Поэтому выбран фиксированный endpoint, а не PAC-сервис |

В двух NetLog тестового CfT для Work встречался `HOST_RESOLVER_MANAGER_REQUEST`. У него были только задачи `[4,9]` — CACHE_LOOKUP и HOSTS — и локальный результат `-105`. Эти записи **не являются доказательством отправленного DNS-пакета**. Для этих Work-запросов сетевой DNS task не наблюдался. Полный захват пакетов на физических/VPN-интерфейсах не проводился; NetLog браузера не показывает DNS самого Python-router и не доказывает отсутствие всех утечек. Не отключали QUIC, WebRTC, защиту сертификатов или secure DNS в пользовательском Chrome ради положительного результата.

## Почему основной Chrome не переводили временно

Действующая политика имеет приоритет над CLI и user Preferences, поэтому эксперимент под ней не доказывает отсутствие политики. Для честной приёмки обычного Chrome её пришлось бы удалить. В текущей macOS `profiles` умеет удалять, а для установки отправляет в Profiles System Settings. Следовательно, **полностью автоматического гарантированного восстановления этого профиля после удаления нет**: установка потребует системного подтверждения пользователя.

При требовании проверенного отката и сохранения текущей базы удалять профиль ради этого исследования не стали. Граница результата — работающий изолированный прототип и точное ограничение управляемого запуска. Основной профиль Chrome, новая живая Passkey/OTP после миграции, browser startup race, обновление Chrome и другие Mac остаются пунктами отдельной приёмки. Это не повод объявлять вариант невозможным, но пока недостаточно для замены beta.6.

Рекомендация по результатам исследования: оставить beta.6 основным способом. Если важнее убрать системный профиль, исследовать дальше сохранённый user pref с явным предупреждением о внутренних настройках Chrome и с заранее согласованным ручным восстановлением managed profile. Launch-only режим годится как дополнительная явная команда, но не как незаметная замена обычного запуска.
