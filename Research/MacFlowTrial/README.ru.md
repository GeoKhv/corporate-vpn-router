# Corporate VPN Router за пределами Chrome: решение для macOS

10 ноября 2026 · Один Mac Apple Silicon, macOS 27.0.1 (26A434), SDK 27.0. База: [v0.2.0-beta.6](https://github.com/GeoKhv/corporate-vpn-router/releases/tag/v0.2.0-beta.6), commit `0fe83ba`. Это отдельный исследовательский каталог.

**Решение: оставить beta.6 основной.** Её транспорт уже работает с другими клиентами, которым можно явно передать HTTP-прокси. macOS также предоставляет механизм прозрачного отбора потоков для приложений без настройки прокси. Но из этого не следует, что все приложения, способы DNS и внешние VPN будут совместимы. На этом Mac ни одна комбинация с нашим активным Network Extension (NE) не проверена: для запуска нет подходящей подписи. Перед разработкой продукта стоит проверить одну новую возможность: доступ из обычного Safari и клиента без настройки прокси к имени, известному только корпоративному DNS.

## Что установлено экспериментально

Исходные данные: [issue #1](https://github.com/GeoKhv/corporate-vpn-router/issues/1), [приёмка beta.6](../../docs/VALIDATION.md), [опыты с системным прокси и отдельным Chrome](../../docs/CHROME-WITHOUT-PROFILE.ru.md). Ранее обычный Chrome под Sota прошёл Work/Life, настоящий отказ корпоративного worker, восстановление и MFA. Прокси на сетевом сервисе Wi-Fi не стал эффективным для Chrome под Sota. Правка Preferences прошла только на лабораторном Chrome for Testing и зависит от внутреннего формата Chromium. Это не решение для Safari.

Новый стенд использует случайный порт на 127.0.0.1 и отдельный экземпляр обработчика CONNECT beta.6. Он допускает только тестовые адресаты. Для Work использует оригинальную проверку поколения SOCKS-worker, SOCKS5 с доменным именем и уже действующий SSL-сеанс. Для Life открывает обычный сокет по маршруту macOS. Каждый запрос идёт из нового процесса; временный флаг имитирует недоступный Work до вызова SOCKS. TLS проверяет клиент, без подмены сертификата. Счётчики подтверждают вход на соответствующую ветку; успех требует ещё и ожидаемого содержимого HTTPS. Стенд не включает transparent proxy, не создаёт utun и не переключает VPN.

| Клиент и способ подключения | Work / Life | При локальном отказе Work | После снятия отказа |
|---|---|---|---|
| curl, явный HTTP CONNECT | Оба ответа проверены | CONNECT для Work вернул 502, Life доступен | Work восстановился |
| Яндекс Браузер 26.8.0.1782, headless, одноразовый профиль, явный HTTP-прокси, QUIC выключен только в тесте | Обе страницы проверены через отдельную вкладку | Ошибка навигации Work, Life загрузился | Work загрузился |
| WKWebView, непостоянное хранилище, явный HTTP CONNECT без failover | HTTP 200 и ожидаемые байты основного ресурса через WebKit | Сетевая ошибка Work, Life загрузился | Work снова вернул ожидаемый ресурс |
| Контроль выхода Life | Публичный HTTPS-свидетель Cloudflare | Тот же видимый IP, что у системного маршрута | IP совпал во всех трёх фазах |

В момент проверки Sota была Connected, маршрут IPv4 по умолчанию шёл в utun. Совпадение выхода относится к одному сервису и времени пробы; оно не заменяет захват на физических интерфейсах, измерение IPv6 или тест всех приложений. Исходную корпоративную сессию не останавливали. Отключение и холодный запуск NE, исчезновение его правил, sleep/reconnect NE, обычный Safari, постоянный профиль Яндекса, корпоративный SSO из этих браузеров и Passkey **не** испытывались. Проверка WebKit использует публичный API [WKWebsiteDataStore.proxyConfigurations](https://developer.apple.com/documentation/webkit/wkwebsitedatastore/proxyconfigurations); стороннее приложение не может так настроить Safari.

Вторая реальная проверка — существующий Xray с loopback SOCKS5 и HTTP CONNECT. Для `example.com` и `www.apple.com` системный маршрут вернул HTTPS 200; через Xray за те же 8 секунд обе цели не завершили TLS ни через SOCKS с удалённым именем, ни через HTTP-прокси. Последний принимал CONNECT (200). Это отрицательный контроль внешнего выхода **до** интеграции с Router. Не установлен источник тайм-аута; это не несовместимость протокола или бренда. Корпоративных имён Xray не передавали. AdGuard VPN установлен; активное системное расширение **AdGuard для Mac** с точкой app-proxy — другой продукт. Shadowrocket с Packet Tunnel сконфигурирован, отключён. Включение альтернативного системного VPN могло вытеснить Sota: эти клиенты не активировались. Установка приложения и состояние «extension enabled» сами по себе не доказывают путь пакетов.

## Что гарантирует Apple и где заканчивается гарантия

- **Уровень потоков.** Для macOS 11+ `NETransparentProxyProvider` получает подходящие исходящие потоки TCP/UDP. Это не IP-маршрутизатор и не второй Packet Tunnel. `NETransparentProxyManager` устанавливает отдельную конфигурацию. Для transparent provider ответ `false` в обработчике означает продолжить штатную отправку. Поэтому Life лучше вообще не включать в правила, а распознанный Work при ошибке **принять и закрыть**, включая случай недоступного worker. Вернуть `false` для такого Work — потенциальный прямой выход. Это не гарантирует блокировку при выгруженном, ещё не стартовавшем или отключённом провайдере. [Семантика Apple](https://developer.apple.com/documentation/networkextension/netransparentproxyprovider).
- **Домены и порты.** Доменное правило Apple с многочастным именем охватывает и поддомены. Разделять exact/tree повторно на потоке и в транспортном gate; для точного правила нельзя молча направить всех соседей по суффиксу в Work. Отдельно описать решения для имени, отсутствующего в метаданных. Правила по адресу/префиксу — другая ось: для тестов нужны отдельные IPv4 и IPv6, /32 и /128 для одиночных адресов. Адресное правило с портом 53 не подходит: SDK требует правило целевого домена для DNS. Запреты на комбинации wildcard адреса/порта, направление outbound и local network заданы в [NETransparentProxyNetworkSettings](https://developer.apple.com/documentation/networkextension/netransparentproxynetworksettings); [примеры доменных правил](https://developer.apple.com/documentation/networkextension/nenetworkrule/init(destinationhost:protocol:)).
- **DNS — главный риск.** При connect-by-name ОС продолжает разрешать имя. `NEDNSSettings` и `NEProxySettings` внутри transparent settings игнорируются. Если внешний DNS возвращает NXDOMAIN для Work, приложение может вообще не открыть TCP-поток; если возвращает адрес, запрос имени мог уже уйти наружу. У вызова по IP или после собственного резолвера `remoteHostname` может отсутствовать. Encrypted DNS/DoH, кэш, DNS HTTPS/SVCB, AAAA и общий IP CDN не дают надёжной обратной привязки к домену. Нельзя отправлять общий IP в Work или Life наугад. Для первого стенда сравнить системный A/AAAA, NXDOMAIN вне организации, IPv6-only, DoH и прямой IP. Для внутреннего имени может понадобиться поддерживаемый *раздельный DNS* с обслуживанием только корпоративной зоны через туннель; текущий SOCKS умеет резолвить внутри CONNECT, но не является DNS-сервером для ОС. Не вводить глобальный DNS proxy, перехват TLS или fake-IP без отдельного обоснования. [Apple о transparent DNS](https://developer.apple.com/documentation/networkextension/netransparentproxyprovider), [remoteHostname](https://developer.apple.com/documentation/networkextension/neappproxyflow/remotehostname).
- **UDP и IPv6.** API доставляет TCP и UDP, а текущий корпоративный gate принимает SOCKS CONNECT по разрешённому имени/порту; голый IPv4/IPv6, UDP ASSOCIATE и туннель IPv6 end-to-end не подтверждены/не предоставляются этим трактом. В кандидате начать с TCP для корпоративных HTTPS; UDP/443 (QUIC) для заведомого Work принять и отклонить. Проверить переход конкретного браузера на TCP и отдельно зафиксировать отказ UDP-only клиента. Life UDP и IPv6 не перехватывать. Охват не распространяется на произвольные пакеты/ICMP. [Текущий транспорт](../../docs/ARCHITECTURE.md).
- **Порядок.** Пользовательский host не может назначить себе первое место. Начиная с macOS 14, администратор может задать `TransparentProxy.Order` в профилях соответствующих transparent proxies. Это порядок **между такими прокси**, не способ переопределить Packet Tunnel, kill switch или контент-фильтр. У per-app VPN также другая область действия. Не найдено гарантии единого порядка для всех классов и конфигураций. [Apple DTS о двух прокси](https://developer.apple.com/forums/thread/796810), [схема Apple](https://github.com/apple/device-management/blob/release/mdm/profiles/com.apple.vpn.managed.yaml), [правила маршрутизации VPN](https://developer.apple.com/documentation/networkextension/routing-your-vpn-network-traffic).
- **Петли и доступ к сессии.** Включать только нужные зоны и порты; исключить петлевые адреса обеих семей, фактический транспорт до корпоративного VPN-шлюза (в том числе если шлюз внутри Work-суффикса), bootstrap/IdP и MFA callback. Учитывать смену адресов шлюза. Выход из provider через отдельный worker — новый поток другого процесса; нельзя полагаться только на автоматическое исключение исходящего трафика самого provider. Проверять счётчиком повторных захватов и конечным тайм-аутом, не прикреплять сокет к физическому интерфейсу в обход внешнего VPN. Системное расширение и пользовательский worker — разные контексты: аутентифицированный IPC с проверкой клиента, пользователя и поколения сессии, особенно при fast user switching. Не открывать всем пользователям корпоративную сессию по одному номеру порта.

## Матрица внешних механизмов

Во всех строках именно **с нашим прозрачным расширением** статус «не проверено». Прогноз ниже — критерий выбора стенда, а не список поддерживаемых клиентов.

| Класс внешней сети | Что известно / что проверять |
|---|---|
| Packet Tunnel, обычный маршрут по умолчанию | Под Sota практически работает явный CONNECT поверх системного выхода. Из вида utun нельзя вывести значения `includeAllNetworks` и `enforceRoutes`. Для NE надо показать, что Work попадает в provider и его SSL до шлюза следует разрешённому пути, а Life сохраняет прежний выход. |
| Split tunnel, специфичные маршруты; традиционный utun/TUN, IKEv2/IPsec | Отбор потоков не требует изменения таблицы маршрутов. Пересечения префиксов, маршруты к публичному шлюзу, DNS и иной исходный интерфейс меняют результат. Сравнить внешнюю и внутреннюю цель, v4/v6 по обеим сторонам границы. WireGuard, OpenVPN и Amnezia классифицировать по реальному режиму, не по имени приложения. Не проверены. |
| Принудительный full tunnel, `includeAllNetworks`, enforced split routes, kill switch | Обычный default route не равен строгому full tunnel. Внешний клиент может ограничить upstream, локальный адрес или трафик при reconnect и остановить Life сам. При этом обходить его политику нельзя. `includeAllNetworks` не поддерживается самим transparent manager. Сохранить Life можно обещать только при работающем внешнем пути. [Apple](https://developer.apple.com/documentation/networkextension/nevpnprotocol/includeallnetworks). |
| Явный локальный HTTP/SOCKS, PAC, системный HTTP proxy, без маршрута ядра | Сокет «напрямую» может обойти внешний прокси; наоборот, если приложение уже соединяется с одним прокси, исходное имя сайта на уровне потока может исчезнуть. Проверять, кому достаётся CONNECT/имя. Опциональный штатный per-client PAC: Work → Router, Life → прежний проверенный прокси/маршрут. Не подменять личный PAC и не добавлять DIRECT fallback к Work. На Xray работающий выход не подтверждён. |
| Другой transparent proxy, DNS proxy, контент-фильтр или per-app VPN | Возможны конкуренция за поток, другой порядок, потеря исходного назначения, блокировка новой связи от worker. Другая политика может действовать по source app: системный сокет worker не тождествен потоку Safari. Статус AdGuard на Mac — только наблюдение. Нужны оба порядка включения и владелец настроек; работа AdGuard VPN, Shadowrocket и других брендов с NE не заявляется. |

## Подпись, установка и откат

На реальном хосте (вне песочницы исследовательского процесса) `security find-identity -v -p codesigning` вернул **0 действительных удостоверений**. В обоих стандартных каталогах пользователя профили provisioning отсутствуют. Есть CLT с SDK и компилятором. Программа без требуемой подписи скомпилировалась и через `loadAllFromPreferences` получила список (1 запись, содержимое не читали); **это не выдаёт право зарегистрировать/запустить собственный provider**. Не запрашивали save/activation, не подделывали entitlements, не отключали SIP/Gatekeeper. Точное препятствие — нет доступного подписанного и разрешённого для этой команды/ID host + provider; установка одного Xcode его не устранит.

Для теста достаточно **доступа к существующей команде Apple Developer** и её действующей development identity/профилям с нужными capabilities для двух отдельных bundle ID, либо готовой надлежаще подписанной тестовой сборки для стенда. Закупка не нужна, если команда уже есть. Для обычной прямой раздачи коллегам (без Mac App Store):

1. Подписать host и вложенный `.systemextension` одной командой с Developer ID Application; запросить нужные provisioning profiles. Для прямой дистрибуции значение Network Extension entitlement — `app-proxy-provider-systemextension`, а у устанавливающего host также `com.apple.developer.system-extension.install`. Конфигурация провайдера указывает точку `com.apple.networkextension.app-proxy`. Не путать значение entitlement с именем provider class. Сверить фактическую подпись и разрешения профилей у обоих targets. Для разработки использовать профиль/значения, выданные Apple для этой сборки. Прямая раздача `.appex` вместо sysex не предусмотрена таблицей Apple.
2. Вложить расширение в `Contents/Library/SystemExtensions`, собрать с hardened runtime, нотариально заверить у Apple (notarization) и приложить ticket для штатного запуска через Gatekeeper. Установить host в `/Applications`; его активация через `OSSystemExtensionRequest` и включение собственной сетевой конфигурации через `NETransparentProxyManager` — разные операции. Требуется разрешение macOS на сетевое расширение и разрешённая конфигурация прокси; на неуправляемом Mac планировать первоначальное подтверждение в System Settings, при необходимости администратором. На управляемом Mac ИТ может заранее разрешить team/bundle ID и развернуть сетевой payload через MDM. Пункты и число диалогов зависят от версии и политик; установка на чистом Mac не проверена. Коллегам не нужны Xcode, собственная developer-подписка или ручное выключение защиты.
3. Предусмотреть отключение и удаление **только своей** NE-конфигурации, деактивацию своего расширения и повторную проверку исходного маршрута. Для MDM управляемую настройку отзывает ИТ. Доступ к системным настройкам расширений и одобрение сетевой конфигурации не заменяют корпоративные TLS/MFA. Переходить в обычном профиле Chrome можно лишь после отдельной приёмки. Для прошлого rollback beta.6 → beta.5 → beta.6 уже выполнялась реальная переустановка; в этом опыте её не повторяли.

[Apple TN3134: варианты поставки](https://developer.apple.com/documentation/technotes/tn3134-network-extension-provider-deployment) · [назначение entitlements и суффикса Developer ID](https://developer.apple.com/forums/thread/786886) · [установка расширения](https://developer.apple.com/documentation/systemextensions/installing-system-extensions-and-drivers) · [notarization](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution) · [MDM для system extensions](https://developer.apple.com/documentation/devicemanagement/systemextensions).

## Стоит ли внедрять

**Сегодня:** предлагать явный HTTP-прокси только клиентам с поддерживаемой настройкой (например, curl, приложение со своим WebKit, отдельный запуск Яндекса). Это даёт пользу без NE-подписи. Порт действующей beta.6 — `127.0.0.1:1091`; стенд проверял тот же обработчик на другом порту. Общий fixed proxy остаётся точкой отказа и для Life, если умрёт сам HTTP-router; в beta.6 он восстанавливается через launchd. У клиента со штатным PAC можно отдавать только Work локальному Router, если доказано, что личный маршрут Life сохраняется. Safari.app не предоставляет нашему приложению настройку своего WKWebsiteDataStore. Системный PAC имеет смысл лишь там, где он действительно эффективен: старый отрицательный опыт с Wi-Fi/Sota остаётся в силе. Не править чужие Preferences. В управляемой организации с готовым MASQUE relay есть ещё [встроенный Network Relay Apple](https://support.apple.com/en-ie/guide/deployment/dep91a6e427d/web) с match domains; текущие SOCKS5 и HTTP/1.1 CONNECT не являются таким сервером. Создавать новую серверную инфраструктуру ради этого опыта нет оснований.

**Если необходим обычный Safari или приложение без настройки прокси:** общими оставить нормализованные правила Work/Life/до входа (exact/tree, порт, действие при отказе), тестовые векторы, проверку TLS/пина, клиент корпоративного SSL и интерфейс подключения по имени. Поверх них — отдельный адаптер macOS для захвата потоков. Не переносить Safari/Яндекс в список доверенных MFA peers автоматически: для browsing достаточно действующей сессии, а нынешний browser callback и его проверки отдельно привязаны к Chrome. Для Windows в будущем нужен собственный адаптер с тем же контрактом; реализация Windows не начиналась. Не использовать PF, маршрут по умолчанию, второй Packet Tunnel или ручные маршруты DNS по IP как замену прозрачному прокси: это меняет внешний VPN и не решает неоднозначность имён ([Apple TN3165](https://developer.apple.com/documentation/technotes/tn3165-packet-filter-is-not-api)).

**Первый критерий продолжения:** на отдельном Mac или VM с доступной подписанной сборкой разместить один подконтрольный Work-домен, доступный только из тестового туннеля, и один публичный Life-контроль. Внешний авторитетный DNS и серверы-свидетели должны позволять отличить отсутствие запроса от утечки; вести наблюдение на utun и физическом интерфейсе тестовой машины. Запустить провайдер с узкими правилами и реальным TCP-мостом, без корпоративных секретов, тестировать Safari и POSIX-клиент, который игнорирует настройки прокси (getaddrinfo + connect), затем Яндекс и Chrome на чистых профилях. Проверить IPv4/IPv6, NXDOMAIN, голый IP/занятый соседями адрес, DoH, QUIC, TLS bootstrap и отсутствие петли. Если внутреннее имя не открывается до захвата или требуется общий перехват DNS, остановиться и отдельно оценить цену DNS-решения.

**Далее, только если первый критерий пройден:** тот же тест на default-route и split Packet Tunnel, затем с enforced/kill switch и при втором прокси; до и после подключения, при падении worker и самого provider, при сне и после рестарта. Сверять и существующие, и новые соединения, внешний IP и отсутствие Work-попыток за пределами туннеля; проверять смену правил, отключение и восстановление исходного пути после удаления. Потерю общего интернета из-за самого внешнего kill switch отличать от ошибки Router. Поддерживаемыми объявлять только прошедшие режимы. Без преимущества над beta.6 в обычном Safari или приложении без proxy дальше не усложнять.

### Воспроизведение текущего опыта

Из корня репозитория, под тем же пользователем, только при уже подключённой beta.6. Для Яндекса нужен установленный браузер; в его отсутствие передать Python только имена нужных контролей: `curl webkit egress`. Стенд сам ничего не устанавливает и не подключает.

```sh
trial_dir="$(mktemp -d)"
xcrun swiftc -parse-as-library Research/MacFlowTrial/WebKitProbe.swift -o "$trial_dir/webkit"
xcrun swiftc -parse-as-library Research/MacFlowTrial/DebugTab.swift -o "$trial_dir/debug-tab"
xcrun clang -fobjc-arc -framework Foundation -framework NetworkExtension Research/MacFlowTrial/ManagerProbe.m -o "$trial_dir/manager"
"$trial_dir/manager"
"$HOME/Applications/Corporate VPN Router.app/Contents/Resources/Runtime/bin/python3.13" -I -B Research/MacFlowTrial/clients.py "$trial_dir/webkit" curl webkit yandex egress
```

Ожидается 15 проверок клиентов и три сравнения выхода, каждое с `passed: true`. `manager` только читает список: количество записей не является критерием допуска. Браузерный профиль удаляется после проверки; в `trial_dir` остаются только лабораторные бинарники. Никаких корпоративных адресов, содержимого страниц или внешних IP в файле результатов нет. Отдельный контроль Xray сопоставлял curl с явными `--proxy socks5h://127.0.0.1:1080`, `--proxy http://127.0.0.1:1087` и `--proxy ""`, во всех случаях с `--noproxy ""`; номера портов относятся только к этому Mac.
